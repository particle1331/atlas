Notes from reading [Designing Multi-Agent Systems](https://www.manning.com/books/designing-multi-agent-systems) by Victor Dibia. The preface explains where the book's pragmatism comes from. Dibia built LIDA, an early LLM system for data visualization, as a fixed four-stage pipeline, and kept running into what pipelines assume: that the right task decomposition is already known and that the task stays put. That frustration led him to conversation-based multi-agent systems and to AutoGen at Microsoft Research, which later grew into the Microsoft Agent Framework. He also carries a scar from the hype cycle: an early LIDA error rate of 20% dropped to 3% after prompt fixes and a new model release, which is why the book pushes a plain engineering stance — task decomposition, systematic evaluation, optimization — over either dismissing agents or over-promising them.

That history shapes the book's choices. It teaches multi-agent systems from first principles by building a small library, picoagents, instead of teaching a framework, and it repeatedly warns that multi-agent is not the right answer for every problem. The four parts follow a theory-build-optimize-apply progression: foundations and patterns, implementation from scratch, evaluation and optimization, then two real-world case studies.

I'm working through it chapter by chapter because it lines up with the orchestration module of my agent study plan: when a single agent loop is enough, and what actually changes when several agents coordinate. The entries summarize each chapter in my own words and record the parts I want to keep — the orchestration patterns and their trade-offs, the design decisions behind building agents from scratch, and the evaluation and protocol questions that decide whether a multi-agent system is reliable. Where a chapter includes runnable examples, I adapt the interesting ones as notebook cells.
